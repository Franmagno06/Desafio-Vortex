## Onde a IA errou

| #   | Sintoma                                | Causa raiz                                        | Como identifiquei     | Correção                           |
| --- | -------------------------------------- | ------------------------------------------------- | --------------------- | ---------------------------------- |
| 1   | `PATCH` zerava o preço do anúncio      | `.default(null)` sobrevive ao `.partial()` do Zod | Script de verificação | `.default` só no schema de criação |
| 2   | Converter venda em doação dava 422     | Validação rodava antes de resolver o preço final  | Teste automatizado    | Reordenar: resolver → validar      |
| 3   | Fail fast com mensagem inútil          | `.min(1, msg)` não cobre variável ausente         | Boot manual           | `z.string({ error: … })`           |
| 4   | `migration.sql` gerado com lixo dentro | `2>&1` misturou o banner do Prisma no arquivo     | Leitura do arquivo    | Capturar apenas stdout             |

**Detalhe #1 — o bug que apagaria preços em produção.** O schema de criação declarava
`priceCents: z.number().nullable().default(null)`, e o de atualização derivava dele com
`.partial()`. Parece seguro, mas `.partial()` torna o campo **opcional** sem remover o
**default**. Consequência: um `PATCH { "status": "RESERVADO" }` saía do parse como
`{ status: 'RESERVADO', priceCents: null }` e apagava o preço de um anúncio de venda sem
ninguém ter pedido.

Peguei isso porque, antes de construir o resto do backend em cima dos schemas, rodei um
script exercitando cada regra e imprimindo o resultado. O caso "PATCH só com status"
mostrou `priceCents: null` na saída. Se eu tivesse confiado no código gerado e seguido em
frente, o bug só apareceria quando um usuário reservasse o próprio anúncio e perdesse o
preço. **Verificar o comportamento vale mais que ler o código e achar que está certo.**

**Detalhe #2 — código inalcançável que parecia correto.** O service tinha um bloco
explícito tratando a conversão de venda em doação:

```ts
if (nextType !== 'VENDA' && current.priceCents !== null) {
  data.priceCents = null;
}
```

Esse bloco nunca era alcançado: três linhas acima, `assertPriceMatchesType()` já lançava
422 comparando o tipo novo com o preço antigo. Ou seja, a IA escreveu a intenção certa e a
ordem errada — e o código _lia_ como se funcionasse. Só o teste automatizado revelou.
Lição: **código inalcançável não avisa que existe.**

**Detalhe #3 — mensagem de erro que não ajuda.** Eu tinha pedido "fail fast com mensagem
clara" e a IA escreveu `.min(1, 'DATABASE_URL é obrigatória...')`. Mas `.min()` só roda
quando o valor **é** uma string; ausente, o Zod dispara o erro de tipo genérico
("expected string, received undefined"). Só descobri subindo o servidor de propósito sem
a variável. O propósito do fail fast é a mensagem dizer o que fazer — sem isso ele vira só
um crash mais cedo.

## O que aprendi

- **`.partial()` do Zod não remove `.default()`.** Um campo pode estar "opcional" e ainda
  assim ser preenchido sozinho no parse. Em rotas de atualização parcial isso é
  destrutivo.
- **Ordem de operações em validação importa.** Validar o estado final exige montar o
  estado final primeiro. Validar cedo demais rejeita transições legítimas.
- **Injeção de dependência não é teoria.** A interface de repositório existe porque o CI
  não tem PostgreSQL — 34 testes rodam em 1,3s sem serviço externo.
- **Dinheiro em centavos.** `0.1 + 0.2 !== 0.3`; inteiro elimina a classe de bug.
- **`200 OK` não é sinônimo de "funcionou".** Continuação da lição da Sprint 0: aqui,
  `/health` responde 200 mesmo com o banco fora — por isso existe `/health/ready`,
  que devolve 503.
- **Redirecionar stderr para dentro de um arquivo gerado o corrompe.** O banner "Update
  available" do Prisma foi parar no meio do SQL da migration.
