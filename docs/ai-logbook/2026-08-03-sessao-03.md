**Detalhe #1 — ordem de validação, de novo.** É a segunda sprint seguida em que a ordem das
operações do Zod causa bug. Na Sprint 1 era validar antes de resolver o preço final; aqui é
validar o formato do e-mail antes de normalizá-lo. O código


lê como se fosse "e-mail, normalizado". O que ele faz é "valide como e-mail, e só então
normalize" — então `"  ana@unifor.br  "` nunca chega à normalização, é rejeitado antes.

Importa na prática: teclado de celular acrescenta espaço depois do autocompletar, e colar um
endereço quase sempre traz espaço junto. O usuário digitou certo e levaria "e-mail inválido".

## O que a IA acertou e vale registrar

O `DUMMY_HASH` contra timing attack eu não teria pedido, porque não conhecia o ataque. A IA
incluiu com a justificativa no comentário, e eu entendi depois de ler:

```ts
const matches = await bcrypt.compare(input.password, user?.passwordHash ?? DUMMY_HASH);
```

Sem isso, login com e-mail inexistente responderia em ~5ms e com e-mail válido em ~250ms —
diferença suficiente para enumerar quem tem conta no sistema **cronometrando as respostas**,
sem acertar uma senha. Cheguei a testar os dois casos e os tempos batem.

É o tipo de coisa que justifica usar IA com senso crítico: ela trouxe, eu conferi, entendi e
mantive — em vez de aceitar cego ou recusar por não conhecer.

| 7   | CI reprovou `format:check` em 6 arquivos que passavam localmente | Formatador do editor reescreveu os arquivos após o meu check, antes do commit | Print do GitHub Actions + `npm run format:check` no commit exato | `npm run format` e recommit          |

**Detalhe #4 — `Record` versus interface.** O TypeScript recusa passar uma `interface` onde se
espera `Record<string, unknown>`, porque interface declarada não tem index signature (um
`type` teria). A tentação é escrever `as any` e seguir. Parei para pensar no requisito real:
a chave de cache do TanStack Query só precisa ser **serializável**. `object` expressa isso sem
forçar a interface a virar um mapa aberto — e sem desligar a checagem de tipos.

**Detalhe #5 — quarta vez que a evidência inicial engana.** A ferramenta que lê o texto da
página não trouxe nenhum card nem os contadores. Antes de "consertar", consultei o DOM
diretamente:

```js
document.querySelectorAll('a[href^="/anuncio/"]').length; // 8
[...document.querySelectorAll('dd')].map((d) => d.textContent); // ["26","8","6","28"]
```

Estava tudo renderizado. A ferramenta é que leu antes da hidratação do React.

inalcançável que parecia funcionar), Sprint 2 (erro que o PowerShell inventou) e agora esta.

## As duas falhas de CI (o clássico "funciona na minha máquina")

Percebi pelos prints do GitHub Actions que o CI vinha **vermelho desde a Sprint 2**, embora
todo o meu portão de qualidade passasse localmente. Dois motivos diferentes, mesma lição.

**Detalhe #6 — `typecheck` falhava por falta de `prisma generate`.** O erro no CI era
`Namespace '.prisma/client'.Prisma' has no exported member 'AnnouncementWhereInput'`, mais um
`Parameter 'row' implicitly has an 'any' type`. Ambos têm a **mesma raiz**: o cliente tipado
do Prisma não existia no runner.

Localmente eu havia rodado `prisma generate` durante a Sprint 1, então o cliente estava lá e o
`tsc` enxergava `Prisma.AnnouncementWhereInput` e inferia o tipo de `row` no `groupBy`. O
runner do GitHub começa do zero: `npm ci` instala os pacotes, mas o cliente do Prisma é um
artefato **gerado**, não versionado. Sem gerá-lo, os tipos somem e o `tsc` quebra.

A correção foi um passo no `ci.yml`, antes do typecheck:

```yaml
- name: Gerar cliente do Prisma
  run: npm run db:generate --workspace @circula/api
```

`prisma generate` lê só o schema — não precisa de `DATABASE_URL` nem de banco. É o passo que
faltava para o CI reproduzir o meu ambiente local.

> Detalhe que me pegou de novo: rodar `prisma generate` localmente para testar deu
> `EPERM: operation not permitted` na DLL do query engine. Não era o comando com problema — era
> o dev server ainda rodando, segurando o arquivo. No Linux do CI, sem processo preso, funciona.

**Detalhe #7 — `format:check` passava local e falhava no CI.** Seis arquivos da landing
reprovavam no Prettier **no commit**, mas o meu `npm run format:check` na Sprint 3 dissera
"All matched files use Prettier code style!".

Não era line-ending (conferi: `git ls-files --eol` mostrou `i/lf w/lf` nos seis). A causa: o
**formatador automático do editor** reescreveu esses arquivos num estilo diferente do Prettier
_depois_ do meu `npm run format`, e eu commitei essa versão. Meu `format:check`, rodado antes
dessa reescrita, deu um falso "tudo certo". O CI, rodando sobre os bytes commitados, pegou.

Reproduzi rodando o Prettier no commit exato (`git rev-parse HEAD` → mesmos 6 arquivos
reprovando) e corrigi com `npm run format` seguido de recommit — desta vez conferindo o
`format:check` **imediatamente antes** do commit, sem janela para o editor interferir.

A lição das duas: **CI verde não é opcional nem cosmético.** Ele existe justamente para pegar o
que passa por acidente no ambiente local. Eu deveria ter olhado o resultado do Actions ao fim
da Sprint 1, e não duas sprints depois.

## O que aprendi

- **JWT não é criptografia.** As duas primeiras partes são base64: decodifiquei o payload do
  meu próprio token sem senha nenhuma. O que ele garante é integridade, não sigilo.
- **A lentidão do bcrypt é o recurso, não o defeito.** 12 rodadas ≈ 250ms por hash, e é
  isso que torna força bruta cara.
- **O bcrypt trunca em 72 bytes silenciosamente** — por isso o `.max(72)` no schema não é
  frescura.
- **Timing attack existe:** vazamento pelo tempo de resposta, não pelo conteúdo dela.
- **Normalizar antes de validar.** `z.string().trim().pipe(z.email())`, nunca o contrário.
- **Isolar a identificação num middleware pagou.** Trocar cabeçalho por JWT mudou um arquivo;
  service, repositório e mapper ficaram intactos.
- **`isPending` ≠ `isFetching`.** O primeiro é "nunca houve dado" (mostra skeleton); o segundo
  é "revalidando com dado na tela" (só esmaece). Confundir os dois faz a lista piscar a cada
  troca de filtro.
- **Toda tela tem quatro estados, não dois.** Carregando, erro, vazio e com dados. O vazio é o
  mais esquecido e o mais visível numa demonstração.
- **Acessibilidade é escolha de estrutura, não auditoria depois.** Usar `<button>` no lugar de
  `<div onClick>` entrega foco por teclado e leitor de tela de graça.
- **`?category=` vazio não é o mesmo que omitir o parâmetro** — o primeiro chega como string
  vazia e é rejeitado pelo enum do Zod.
