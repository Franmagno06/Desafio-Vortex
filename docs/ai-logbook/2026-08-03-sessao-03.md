## Onde a IA errou

| #   | Sintoma                                 | Causa raiz                                              | Como identifiquei     | Correção                            |
| --- | --------------------------------------- | ------------------------------------------------------- | --------------------- | ----------------------------------- |
| 1   | Login com e-mail em maiúsculas dava 422 | `z.email()` valida ANTES do `.transform()` que faz trim | Teste automatizado    | `z.string().trim().pipe(z.email())` |
| 2   | Erro parecia truncado: `Bearer .`       | O PowerShell removeu `<token>` achando que era tag HTML | Comparação com `curl` | Nenhuma — a API estava correta      |
| 3   | `JWT_SECRET` "já existia" mas não subia | Estava comentado no `.env` desde a Sprint 1             | Boot falhou           | Descomentar com segredo gerado      |

**Detalhe #1 — ordem de validação, de novo.** É a segunda sprint seguida em que a ordem das
operações do Zod causa bug. Na Sprint 1 era validar antes de resolver o preço final; aqui é
validar o formato do e-mail antes de normalizá-lo. O código

```ts
z.email().transform((v) => v.trim().toLowerCase());
```

lê como se fosse "e-mail, normalizado". O que ele faz é "valide como e-mail, e só então
normalize" — então `"  ana@unifor.br  "` nunca chega à normalização, é rejeitado antes.

Importa na prática: teclado de celular acrescenta espaço depois do autocompletar, e colar um
endereço quase sempre traz espaço junto. O usuário digitou certo e levaria "e-mail inválido".

**Detalhe #2 — a ferramenta de diagnóstico mentiu.** Ao testar sem token, o PowerShell
mostrou:

```
"message":"Envie o cabeçalho Authorization: Bearer ."
```

O `<token>` tinha sumido. Parecia bug de template string. Antes de mexer, conferi com outro
cliente:

```powershell
curl.exe -s http://localhost:4000/api/v1/auth/me
# {"error":{"code":"UNAUTHORIZED","message":"Envie o cabeçalho Authorization: Bearer <token>."}}
```

A API estava certa o tempo todo. O `$_.ErrorDetails.Message` do PowerShell tenta interpretar
a resposta como HTML e engoliu o que parecia uma tag.

Terceira vez neste projeto que a evidência inicial engana — Sprint 0 (`200 OK` do servidor
errado), Sprint 1 (código inalcançável que parecia funcionar) e agora um erro inexistente.
Virou regra pessoal: **confirmar com uma segunda fonte antes de "corrigir".**

## O que a IA acertou e vale registrar

O `DUMMY_HASH` contra timing attack eu não teria pedido, porque não conhecia o ataque. A IA
incluiu com a justificativa no comentário, e eu entendi depois de ler:

```ts
const matches = await bcrypt.compare(input.password, user?.passwordHash ?? DUMMY_HASH);
```

Sem isso, login com e-mail inexistente responderia em ~5ms e com e-mail válido em ~250ms —
diferença suficiente para enumerar quem tem conta no sistema **cronometrando as respostas**,
sem acertar uma senha. Cheguei a testar os dois casos e os tempos batem.

É o tipo de coisa que justifica usar IA com senso crítico: ela trouxe, eu conferi, entendi e
mantive — em vez de aceitar cego ou recusar por não conhecer.

## O que aprendi

- **JWT não é criptografia.** As duas primeiras partes são base64: decodifiquei o payload do
  meu próprio token sem senha nenhuma. O que ele garante é integridade, não sigilo.
- **A lentidão do bcrypt é o recurso, não o defeito.** 12 rodadas ≈ 250ms por hash, e é
  isso que torna força bruta cara.
- **O bcrypt trunca em 72 bytes silenciosamente** — por isso o `.max(72)` no schema não é
  frescura.
- **Timing attack existe:** vazamento pelo tempo de resposta, não pelo conteúdo dela.
- **Normalizar antes de validar.** `z.string().trim().pipe(z.email())`, nunca o contrário.
- **Isolar a identificação num middleware pagou.** Trocar cabeçalho por JWT mudou um arquivo;
  service, repositório e mapper ficaram intactos.
