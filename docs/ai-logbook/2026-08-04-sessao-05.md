## Onde a IA errou

| #   | Sintoma                                    | Causa raiz                                            | Como identifiquei          | Correção                                  |
| --- | ------------------------------------------ | ----------------------------------------------------- | -------------------------- | ----------------------------------------- |
| 1   | Tela presa em skeletons para sempre        | React Query **pausa** a query em falha de rede        | Teste com a API fora do ar | `networkMode: 'always'` + tratar `paused` |
| 2   | Botão "Tentar de novo" não fazia nada      | Query pausada ignora `refetch()`                      | Clique não recuperava      | `resetQueries` em vez de `refetch`        |
| 3   | Ícone do PWA virou uma mancha branca       | Folha desenhada com preenchimento em vez de traço     | Olhando o PNG gerado       | Traçado do lucide, com `stroke`           |
| 4   | `require` dentro do Service Worker         | Não existe `require` num SW em ESM                    | Revisão antes do build     | Import normal no topo                     |
| 5   | Manifesto parecia corrompido (`Circula �`) | Console do Windows (cp1252) não renderiza o travessão | Leitura dos **bytes**      | Nenhuma — o arquivo estava certo          |

**Detalhe #1 e #2 — o erro de método, não de código.** Este foi o problema mais
difícil do projeto até aqui, e o mais instrutivo pelo **jeito errado** como começou.

Sintoma: com a API fora do ar, `/explorar` ficava com 72 skeletons para sempre. Sem
erro, sem mensagem, sem saída.

A IA tentou consertar **duas vezes por dedução**, e errou nas duas:

1. Primeiro achou que era `networkMode` pausando por offline e mudou para
   `offlineFirst`. Rebuild, teste: **continuou travado**.
2. Depois achou que o `onlineManager` estava dessincronizado e forçou
   `setOnline(false) → setOnline(true)`. Rebuild, teste: **continuou travado**.

Só na terceira tentativa ela instrumentou o estado real, com um build de depuração:

```json
{ "isPending": true, "isError": false, "fetchStatus": "paused" }
```

E, no clique do botão:

```json
{ "onlineAntes": true, "onlineDepois": true, "fetchStatus": "paused" }
```

Aí ficou claro: o React Query tem um **quarto estado** que eu não conhecia —
`pending` + `fetchStatus: 'paused'`. Nele a query não erra, não tenta de novo e
**ignora `refetch()`**. E o `onlineManager` já dizia `true` o tempo todo, o que
derrubou de vez a segunda hipótese.

O que eu tiro disso: **duas correções foram aplicadas sem medir nada**. Cada uma
custou um build e um ciclo de teste, e nenhuma tinha base em evidência. A terceira,
feita depois de instrumentar, acertou de primeira. A regra que fica é a mesma que já
apareceu em outras sprints, agora num caso onde ignorá-la custou caro: **meça antes de
corrigir**.

A correção final também é boa de explicar, porque é uma decisão de arquitetura e não um
remendo: `networkMode: 'always'` diz ao React Query para nunca pausar por achar que
está sem rede — porque **quem responde offline nesta aplicação é o Service Worker**.
Uma requisição sem internet pode perfeitamente ter sucesso pelo cache. Cada camada com
sua responsabilidade.

**Detalhe #5 — quinta vez que a ferramenta engana.** O manifesto parecia ter encoding
quebrado (`"name":"Circula � Economia..."`). Antes de "corrigir", li os bytes crus:
`b'Circula \xe2\x80\x94 Economia'` — que é exatamente o travessão em UTF-8 correto. O
problema era o console do Windows (cp1252) não conseguir **exibir** o caractere.

Somando o projeto: Sprint 0 (`200 OK` do servidor errado), Sprint 1 (código
inalcançável), Sprint 2 (erro inventado pelo PowerShell), Sprint 3 (vitrine "vazia") e
agora esta. **Cinco vezes.** Já não é coincidência: é uma regra de trabalho.

## O que a IA acertou e vale registrar

O **Background Sync** eu não teria pedido, porque não sabia que existia. A IA incluiu
com a justificativa no comentário: se a pessoa toca em "Publicar" sem rede, a
requisição vai para uma fila no IndexedDB e o navegador **a reenvia sozinho quando a
conexão voltar — mesmo que o app já tenha sido fechado**.

É o recurso que mais separa "site que quebra offline" de "aplicativo de verdade", e vai
render um bom momento no vídeo.

Também vale registrar o cuidado com o ícone `maskable`: eu não sabia que o Android
recorta o ícone na forma do sistema e que isso exige uma arte com margem de segurança.
Usar a mesma imagem para os dois propósitos teria deixado o ícone cortado no celular —
exatamente na demonstração de instalação que o edital pede.

## O que aprendi

- **Service Worker é um proxy entre o app e a rede**, rodando em outra thread. Não tem
  `window` nem `document`; o global é `self`.
- **Cada tipo de recurso pede uma estratégia diferente:** stale-while-revalidate para
  listagens, network-first para sessão, cache-first para imagem.
- **Toda query tem quatro estados, não três.** `pending` + `paused` é invisível se a
  interface só olhar `isPending`.
- **`refetch()` não desbloqueia query pausada** — `resetQueries` sim, porque começa do
  zero em vez de continuar um retryer travado.
- **`gcTime` precisa ser maior que o intervalo entre sessões** para o cache persistido
  ter o que restaurar. Com 5 minutos, não sobra nada ao reabrir o app.
- **Ícone `maskable` é outra arte**, não a mesma imagem com outro nome.
- **Medir antes de corrigir.** Duas correções por dedução falharam; a instrumentação
  resolveu na primeira.
