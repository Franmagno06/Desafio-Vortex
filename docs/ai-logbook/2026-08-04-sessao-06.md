## Onde a IA errou

| #   | Sintoma                               | Causa raiz                                    | Como identifiquei         | Correção                          |
| --- | ------------------------------------- | --------------------------------------------- | ------------------------- | --------------------------------- |
| 1   | Regex frágil no rewrite da Vercel     | Excluía assets à mão, sem necessidade         | Revisão antes de publicar | Catch-all simples                 |
| 2   | Script de teste falhou lendo o `.env` | O valor está entre aspas; o parse não tratava | Erro no PowerShell        | Deixar o `dotenv` do app carregar |

**Detalhe #1 — complexidade que não pagava nada.** A primeira versão do `vercel.json`
tinha um rewrite com _negative lookahead_ listando tudo que **não** deveria cair no
`index.html`:

```
/((?!assets/|icons/|favicon|manifest|sw\.js|registerSW\.js|workbox-).*)
```

Funciona, mas é frágil: esquecer um item na lista quebra silenciosamente um arquivo — e
se o esquecido for o `sw.js`, o PWA inteiro para de atualizar. Pior: só apareceria em
produção.

A Vercel **checa o sistema de arquivos antes de aplicar rewrites**, então um catch-all
simples já serve os assets normalmente:

```json
{ "source": "/(.*)", "destination": "/index.html" }
```

Menos código, menos superfície para errar, mesmo resultado. Vale como lembrete de que
código "esperto" que resolve um problema que a plataforma já resolve é dívida, não
sofisticação.

**Detalhe #2 — errar o caminho mais curto.** Para testar a API em modo produção, a IA
tentou extrair `DATABASE_URL` e `JWT_SECRET` do `.env` com regex no PowerShell. Quebrou
porque os valores estão entre aspas.

A correção foi perceber que o **esforço era desnecessário**: a própria aplicação carrega
o `.env` via `dotenv`, e o `dotenv` não sobrescreve variáveis já definidas no ambiente.
Bastava rodar com `NODE_ENV=production CORS_ORIGINS=... node dist/server.js` e deixar o
resto vir do arquivo.

## O que a IA acertou e vale registrar

Duas coisas que eu não teria pensado sozinho:

**Migrations antes de aceitar tráfego.** O `start:prod` é
`prisma migrate deploy && node dist/server.js`. O `&&` importa: se a migration falhar, o
servidor **não sobe**. E a ordem evita uma janela de segundos em que o código é novo e o
schema do banco é velho — janela em que toda requisição que tocasse a coluna nova
quebraria.

**O cache que congelaria a aplicação.** O `sw.js` precisa ir com `max-age=0`. Se fosse
cacheado como os outros arquivos, o navegador guardaria o Service Worker antigo — que
serve o app antigo do **precache dele** — e nenhum deploy chegaria ao usuário. É um bug
que não aparece para quem desenvolve, porque o DevTools costuma estar com "Update on
reload" ligado.

## O que aprendi

- **Infraestrutura como código** vale pelo mesmo motivo que código versionado vale:
  histórico do que mudou e possibilidade de recriar do zero.
- **`sync: false`** é como um blueprint público declara "esta variável existe, mas o
  valor não está aqui".
- **`migrate deploy` ≠ `migrate dev`.** O segundo pode recriar o banco; nunca em
  produção.
- **Variáveis `VITE_*` são públicas e congeladas no build.** Mudar no painel sem
  redeploy não tem efeito, e segredo nenhum pode ir nelas.
- **Service Worker não pode ter cache longo**, ou a aplicação congela numa versão velha.
- **O plano gratuito da Render hiberna em 15 minutos** — e 40 segundos de tela branca
  arruinariam a demonstração do vídeo.
- **Verificar produção localmente é possível e barato:** rodar o build compilado com
  `NODE_ENV=production` revelou que o CORS realmente bloqueia localhost e que o stack
  trace não vaza.
